# Ping Assistant

Bun/TypeScript MCP channel server для Claude Code: читает Slack, подкладывает айтемы в
сессию через `notifications/claude/channel` и общается с пользователем через Telegram-бота.
Дизайн: `docs/superpowers/specs/2026-10-19-ping-assistant-design.md`.

## Установка

### Что нужно

- [bun](https://bun.sh) в `PATH` той оболочки, из которой запускается `claude`;
- `caffeinate` (есть в macOS из коробки) — launcher не даёт Маку заснуть, пока сессия жива;
- Claude Code с поддержкой `--channels`.

```bash
bun install
bunx tsc --noEmit   # проверка типов
bun test            # тесты (стабильно без шума в stderr)
```

### Slack-приложение

1. На https://api.slack.com/apps → *Create New App* → *From scratch*, выбрать воркспейс.
2. *OAuth & Permissions* → **User Token Scopes** (именно user, не bot):
   `channels:history channels:read groups:history groups:read im:history im:read mpim:history mpim:read users:read search:read chat:write files:read`
3. *Install to Workspace* и подтвердить.
4. Токен `xoxp-…` лежит там же, в *OAuth & Permissions* → **User OAuth Token**.
   Сообщения уходят от твоего имени, без бейджа приложения.
5. Socket Mode (сообщения приходят за секунды, а не раз в `pollSeconds`; без него сервер просто опрашивает Slack):
   - *Socket Mode* → **Enable Socket Mode**;
   - *Basic Information* → **App-Level Tokens** → *Generate Token and Scopes*, scope `connections:write`;
     получится токен `xapp-…`;
   - *Event Subscriptions* → **Enable Events** → *Subscribe to events on behalf of users*:
     `message.channels`, `message.groups`, `message.im`, `message.mpim` (Request URL не нужен);
   - если Slack попросит, переустановить приложение (*Reinstall to Workspace*);
   - положить токен в `.env` как `SLACK_APP_TOKEN=xapp-…` (см. «Секреты»).

   `slack-app-manifest.json` уже включает Socket Mode и эти четыре события.

### Telegram-бот

1. В @BotFather: `/newbot`, выбрать имя, скопировать токен вида `123456:ABC…`.
   **Только новый бот для Ping Assistant.** Не бери токен бота официального telegram-плагина
   Claude Code (или любого другого): Telegram отдаёт обновления одному поллеру на токен, второй
   получает 409 Conflict. После восьми 409 подряд поллер Ping Assistant останавливается и
   присылает «⛔ Telegram-поллер остановлен (409): другой процесс держит токен бота.
   Перезапусти ping-assistant.» — кнопки и команды до перезапуска не работают.
2. Числовой chat id (это `telegramChatId`; бот отвечает только в личке с этим id):
   - написать любое сообщение своему боту и открыть
     `https://api.telegram.org/bot<TOKEN>/getUpdates` — id в `message.chat.id`; или
   - спросить у @userinfobot.

### Секреты

`~/.config/ping-assistant/.env` (права `600`, в репозиторий не попадает):

```
SLACK_USER_TOKEN=xoxp-…
TELEGRAM_BOT_TOKEN=123456:…
# необязательно: Socket Mode
SLACK_APP_TOKEN=xapp-…
# необязательно: статусы Jira-тикетов в айтемах (токен: id.atlassian.com → Security → API tokens)
JIRA_EMAIL=you@scentbird.ai
JIRA_API_TOKEN=…
```

Комментарий в конце строки отделяется пробелом: `KEY=value # …`. Без `SLACK_APP_TOKEN` сервер пишет в stderr `ping-assistant: SLACK_APP_TOKEN not set, polling only`
и работает только опросом.

Те же переменные из окружения имеют приоритет над файлом. Без пары `JIRA_EMAIL` + `JIRA_API_TOKEN`
сервер не ходит в Jira (в stderr `JIRA_EMAIL/JIRA_API_TOKEN not set, Jira keys left to the session`):
ключи тикетов сессия смотрит сама через Atlassian MCP.

### Конфиг

```bash
cp ping-assistant.config.example.json ping-assistant.config.json
```

Другой путь — переменная `PING_ASSISTANT_CONFIG`. Поля:

| Поле | Смысл |
|---|---|
| `userId` | твой Slack member ID: профиль → ⋯ → *Copy member ID* |
| `watchChannels` | ID каналов (`C…`), где отслеживаются треды; личка, группы-личек и упоминания читаются всегда |
| `telegramChatId` | числовой chat id из шага выше, строкой |
| `scentbirdRepoPath` | локальный клон репозитория; сессия читает из него код для разбора вопросов |
| `pollSeconds` | период опроса Slack без Socket Mode (60) |
| `drainSeconds` | с Socket Mode: период тика, который разбирает пришедшие по сокету сообщения (5) |
| `socketReconcileTicks` | с Socket Mode: опрос Slack (сверка) идёт раз в столько тиков, пока сокет подключён (10) |
| `settleSeconds` | сколько ждать после последнего сообщения собеседника, прежде чем разбирать (90) |
| `maxSettleSeconds` | потолок ожидания от первого сообщения (300) |
| `followUpDays` | сколько дней после твоей отправки следить за тредом (7) |
| `contextMessages` | сколько сообщений контекста подтягивать к айтему (30) |
| `triageTimeoutSeconds` | через сколько секунд без разбора прислать «⏳ #N без разбора» и разбудить сессию ещё раз (600) |
| `dryRun` | `true`: ничего не отправляется в Slack, в Telegram приходит «🧪 dry-run, отправил бы …» |
| `feedbackReviewCron` | когда присылать сессии недельный разбор фидбека: `{ "weekday": 1, "hour": 9, "minute": 30 }` — понедельник 09:30 по системной таймзоне (`weekday`: 0 = воскресенье … 6 = суббота). Если за 7 дней фидбека нет, разбора нет |
| `briefing` | утренний брифинг: `{ "hour": 9, "minute": 30, "weekdays": [1, 2, 3, 4, 5] }` — в 09:30 по системной таймзоне по будням (`weekdays`: 0 = воскресенье … 6 = суббота, хотя бы один, без повторов). Любое поле можно опустить — возьмётся значение по умолчанию |
| `selfDmTest` | только вместе с `dryRun: true`: сообщения в личке с самим собой считаются чужими, чтобы тестировать без коллег (`false`) |
| `statePath` | файл состояния (`~/.config/ping-assistant/state.json`) |
| `github` | `{ "defaultRepo": "scentbird/scentbird" }`: в каком репозитории искать PR, упомянутый как «PR #15110» без ссылки |
| `jira` | `{ "site": "scentbird.atlassian.net" }`: хост Jira для ссылок и REST-запросов |

**Начинай с `"dryRun": true`.**

### voice.md

`voice.md` в корне проекта (раздел 7 спецификации) задаёт твой голос в ответах. Он
готовится отдельно. Пока его нет, варианты нейтральные, а `analysis` заканчивается
строкой «voice.md не найден».

### База знаний (локально)

Сессия перед ответами на `product`/`org`-вопросы читает локальный дамп рабочих каналов
(правило — в `CLAUDE.md`, §4 «Ресёрч по типу»):

```bash
bun run scripts/slack-dump.ts --channel C037W1VUY7P --channel C06SXAF4HAL --since 2026-07-01
```

- Читает Slack (только чтение) тем же `SLACK_USER_TOKEN` из `~/.config/ping-assistant/.env`:
  историю каналов, все треды, имена людей и каналов. Темп — не больше 40 запросов в минуту,
  чтобы не мешать работающему серверу; 429 переживает с повтором.
- Пишет `knowledge/slack/<канал>/<YYYY-MM>.md` (сообщения по месяцам, ответы в тредах с
  отступом, время Europe/Berlin, permalink под каждым сообщением) и `index.md` со счётчиками.
  Боты и служебные сообщения (вход/выход, смена темы) пропускаются.
- `knowledge/context.md` — сводка по дампам (глоссарий, люди, хронология решений, открытые
  темы); пишется вручную/сессией Claude, скрипт её не трогает.
- **`knowledge/` в `.gitignore`**: там могут быть приватные сообщения, не коммить его.
- Обновление: та же команда без `--since` — инкрементально, от последнего сообщения в дампе
  минус сутки (окно начинается с начала месяца, затронутые месяцы перезаписываются целиком).
  Новые ответы в тредах более ранних месяцев так не подтягиваются — для них запусти с
  `--since` нужной даты.

## Запуск

```bash
bin/ping-assistant-up
```

Это `caffeinate -i claude --setting-sources project --permission-mode dontAsk --dangerously-load-development-channels server:ping-assistant`,
запущенный из корня проекта; дополнительные аргументы пробрасываются в `claude`. Сервер объявлен
в `.mcp.json` проекта (`enableAllProjectMcpServers: true` в настройках проекта снимает вопрос об
одобрении), а флаг `--dangerously-load-development-channels` делает его каналом. Путь через
плагин (`--plugin-dir . --channels plugin:ping-assistant@local`) не работает: канал
`plugin:…` требует *установленного* плагина из маркетплейса, `--plugin-dir` установкой не считается,
и CLI пишет «plugin not installed» и «not on the approved channels allowlist». Инструменты сессии
называются `mcp__ping-assistant__<tool>`.
Первый тик (через `pollSeconds`, с Socket Mode — через `drainSeconds`) ставит курсоры на «сейчас», прошлое не разбирается.

Модель сессии задаёт `PING_ASSISTANT_MODEL` (по умолчанию `claude-sonnet-5-5`; например,
`PING_ASSISTANT_MODEL=claude-opus-5-5 bin/ping-assistant-up` или `claude-fable-5-1`); launcher
передаёт её в `claude --model`. Идея эскалации: сессия на дешёвой модели занимается триажем, а
ресёрч и черновики вариантов для сложных айтемов (technical/product, несколько вопросов,
файлы, низкая уверенность) делает субагент на Opus; правила — в `CLAUDE.md`, раздел «Модели и
эскалация».

### Как работает: Socket Mode и опрос

С `SLACK_APP_TOKEN` сервер держит WebSocket Socket Mode (`apps.connections.open`): события
`message.*` приходят за секунды, подтверждаются сразу и складываются в очередь. Тик идёт каждые
`drainSeconds` и разбирает очередь теми же фильтрами, что и опрос (боты, служебные и скрытые
подтипы — правки, вступления, отметки «есть ответ»; дедуп по `channel+ts`); источник — личка,
группа-личка, упоминание `<@userId>` (в том числе в канале из `watchChannels`), канал из
`watchChannels` или тред под наблюдением, остальное отбрасывается. Slack такие тики не опрашивают
(кроме кэшируемых имён и permalink). Айтем по-прежнему созревает через `settleSeconds` после
последнего сообщения.

Опрос остаётся сверкой: пока сокет подключён, он идёт раз в `socketReconcileTicks` тиков
(при 5 с и 10 — раз в 50 с) и сразу после каждого (пере)подключения, чтобы дочитать пропущенное,
пока сокет лежал. Пока сокет отключён, опрос идёт каждый тик. Сокет переподключается сам
(пауза 1 → 15 с; на `disconnect` от Slack — через 1 с). После сна мака или смены сети соединение
может молча повиснуть, поэтому оно пересоздаётся, если между тиками прошло больше
2 × `drainSeconds` или по нему 10 минут не пришло ни одного кадра. Если WebSocket умеет `ping()` (Bun умеет),
сервер шлёт ping раз в 60 с и считает pong кадром; правило 10 минут тишины остаётся запасным. Неисправимые ошибки
открытия (`invalid_auth`, `not_allowed_token_type` и т. п.) пишутся в лог один раз, дальше только опрос:
тик переходит на `pollSeconds`, в логе `socket gave up: polling every <pollSeconds>s`.
Сообщение из сокета сдвигает курсор разговора, только если опрос уже читал этот разговор в
текущем соединении; иначе сверка пропустила бы сообщения, пришедшие, пока сокет лежал.

Сокет видит больше, чем опрос: ответы в тредах личек и групп-личек, а также ответы в тредах
под старыми (старше `followUpDays`) сообщениями каналов из `watchChannels` приходят айтемами. Один опрос их не нашёл бы:
история лички не показывает ответы в тредах, а окно канала ограничено `followUpDays`. Так задумано.

Отчёт о старте и остановке: после запуска опроса Telegram и `hello` сокета (или через 20 с, что раньше) сервер один раз шлёт в Telegram «✅ Ping Assistant запущен» (режим, состояние сокета, Slack-аккаунт из `auth.test`, модель сессии, число открытых вопросов); при штатной остановке (stdin, SIGTERM, SIGINT, SIGHUP) — «⏹ Ping Assistant остановлен», не дольше 2 с.

Новые сообщения в личках находятся одним поиском за тик (`search.messages`, `is:dm`): читаются
только лички, где поиск что-то нашёл. Индекс поиска Slack может отставать до минуты, так что
сообщение иногда приходит на тик позже. Групповые лички (MPIM) с активностью за сутки читаются
каждый тик, остальные — раз в 10 тиков; все прочие лички страхуются полным обходом раз в 30 тиков.

Два флага безопасности, без них гарантия «ничего не уходит без подтверждения» не механическая:

- `--setting-sources project`: действует только `.claude/settings.json` проекта. Пользовательские
  разрешения с этого мака (например, `Bash(python:*)`, `Bash(curl:*)`) в сессию не попадают,
  значит модель не может прочитать токен из `~/.config/ping-assistant/.env` и постить в Slack
  мимо сервера. Нужные сессии плагины включены в `enabledPlugins` проекта (сейчас только Atlassian).
- `--permission-mode dontAsk`: всё, что не разрешено явно, отклоняется, а не ждёт ответа
  в терминале. Иначе один запрос прав заморозил бы безнадзорную сессию.

Дополнительно `.claude/settings.json` запрещает интерпретаторы (`python`, `node`, `bun`, `curl`…)
и чтение каталога `~/.config/ping-assistant/` инструментами `Read`/`Grep`/`Glob`.

Логи: stderr сервера (Claude Code пишет его в логи MCP-сервера, видно с `claude --debug`).
В них только виды событий, без текста сообщений. Состояние: `~/.config/ping-assistant/state.json`.
Раз в час из него удаляются закрытые айтемы (отправлен, пропущен, отклонён, отвечено вручную) старше `followUpDays` и старые записи дедупа; открытые айтемы не трогаются.

Спросить сессию, что отсеяно: «что ты проигнорировал за сегодня?» (инструмент `list_ignored`,
список с причинами); «что висит?» — `list_items`.

### Как работает: ссылки на тикеты и PR

Перед доставкой айтема сервер ищет в его сообщениях и контексте ключи Jira (`PF-4282`, до 5) и
PR (`https://github.com/<owner>/<repo>/pull/<n>`, а также `#15110` в строке со словом PR/пр/pull —
тогда из `github.defaultRepo`, до 5) и за ~6 с суммарно получает их статус: PR — через `gh api`
(нужен установленный и залогиненный `gh`, иначе PR пропускаются, в логе один раз
`references: gh unavailable, PRs omitted`), Jira — через REST, только с `JIRA_EMAIL`/`JIRA_API_TOKEN`.
Результат уходит сессии в `references` айтема (то, что получить не удалось, — в `unresolved`),
хранится в айтеме (повторно используется в `revise` и в follow-up в течение 30 минут), а в
Telegram под цитатой появляются до трёх строк вида `🔗 PF-4282 · In QA · Philipp`. Ошибки
пишутся в лог только именем, доставку они не задерживают дольше этого бюджета.

### Как работает: память треда и договорённости

Если айтем в треде (в личке — ещё если в контексте ≥ 6 сообщений; у сообщения канала вне треда —
только при более ранних айтемах или сохранённой сводке), сервер добавляет в JSON айтема блок
`thread`: число сообщений, участники, сколько и когда писал Илья, первое и последнее сообщение,
длительность в днях и `prior_items` — более ранние айтемы этой цепочки follow-up или этого
разговора (статус, что отправлено). Для длинного треда сессия пишет в разборе блоки
«Договорённости:» и «Открыто:» (в Telegram они жирные, как «Тип:»), а после `propose` сохраняет
их сводку инструментом `remember_thread` (до 1200 символов, `state.threads` по ключу разговора).
Следующие айтемы того же разговора получают её в `thread.agreements` с `updated_at`, и сессия
сверяет только то, что написано позже. Сводки, не обновлявшиеся `followUpDays × 4` дней,
удаляются при ежечасной чистке.

### Как работает: утренний брифинг

В настроенные дни (`briefing`, по умолчанию будни 09:30 по системной таймзоне) сервер один раз
присылает сессии `kind: briefing` — JSON со сводкой с прошлого брифинга (в понедельник — с пятничного), но не дальше 7 дней
назад; если брифинга ещё не было — за 24 часа (`since`): что проигнорировано (`ignored_total` — сколько всего, и до 20 последних с причинами), что ждёт решения Ильи
(с возрастом и первыми 80 символами первого сообщения: Slack-разметка раскрыта, `:emoji:` заменены на эмодзи или убраны), что застряло в `settling`/`triage`
дольше `triageTimeoutSeconds`, что отправлено и на что Илья ответил сам, сколько записано
фидбека. У каждого айтема есть короткое имя канала (`личка`, `группа` или имя без `#` и префикса `proj-scentbird-`/`proj-`, до 18 символов) и ссылка на первое сообщение. Время закрытия айтема хранится в `closedAt`; у айтемов, закрытых до его появления,
берётся последняя известная активность. Первый запуск только запоминает время
(`state.lastBriefingAt`); пропущенные во сне моменты дают один брифинг при пробуждении; если
сессия недоступна, повтор не чаще раза в минуту, в лог — одна строка на серию сбоев. Сессия
собирает из этого одно HTML-сообщение «☀️ Брифинг …» (`say` с `format: 'html'`: жирные заголовки
разделов, номер айтема — ссылка в Slack, под каждым айтемом строка-сводка; если Telegram не разберёт
разметку, сообщение уйдёт без тегов) и добавляет встречи на сегодня из
Google Calendar (только чтение, `list_events`). Сообщение «брифинг» в Telegram присылает то же
сразу, не сдвигая расписание.

## Автозапуск и иконка

Сессия Claude Code должна жить постоянно, а ей нужен TTY, поэтому её держит tmux.

```bash
bin/ping-assistant-session             # подключиться к сессии (создать, если её нет; включает автозапуск, если он снят)
bin/ping-assistant-session --detached  # только убедиться, что сессия запущена (для launchd)
bin/ping-assistant-stop                # выключить полностью: снять автозапуск и сторожа, погасить сессию
```

Скрипт создаёт tmux-сессию `ping-assistant` с `bin/ping-assistant-up` из корня репозитория. PATH с
`~/.bun/bin`, `/opt/homebrew/bin` и каталогом `claude` записывается в окружение сессии, чтобы `bun` и
`claude` находились и под launchd. Отключиться, не останавливая сессию: `Ctrl-b d`.

### Иконка

`bin/Ping Assistant.command` открывает Terminal и подключается к сессии. Двойной клик в Finder
запускает его (при первом запуске macOS может спросить подтверждение). Чтобы иконка была под рукой:

- перетащи файл на Dock (справа от разделителя) или на Рабочий стол с зажатыми Option+Cmd, это создаст алиас;
- либо в Finder: правая кнопка по файлу, «Создать псевдоним», и перенеси псевдоним куда удобно.

Вторая иконка, `bin/Ping Assistant Stop.command`, выключает всё: снимает оба launchd-агента (иначе сессия
поднялась бы снова через 5 минут, а сторож начал бы слать «не запущен»), гасит tmux-сессию и ждёт Enter.
Обратно включает первая иконка: она создаёт сессию и, если автозапуск снят, ставит агентов заново.
Закрыть окно сессии без выключения — просто закрыть Terminal: это только отцепиться.

Закрытие окна Terminal только отсоединяет клиент: сессия tmux и Claude продолжают работать.

### Автозапуск при входе (launchd)

Шаблоны лежат в `launchd/`. Пути в них прописаны под эту машину (`/Users/ilebedyuk/projects/ping-assistant`,
`/Users/ilebedyuk/.bun/bin/bun`, PATH с `/opt/homebrew/bin`); на другой машине их нужно отредактировать
до копирования.

- `com.ping-assistant.session.plist` запускает `bin/ping-assistant-session --detached` при входе и каждые
  300 секунд (не KeepAlive: сессию держит tmux, а перезапуск по интервалу поднимает её после падения).
  Лог: `~/Library/Logs/ping-assistant/session.log`.
- `com.ping-assistant.watchdog.plist` каждые 300 секунд запускает `bun run scripts/watchdog.ts`.
  Лог: `~/Library/Logs/ping-assistant/watchdog.log`.

Установка:

```bash
mkdir -p ~/Library/Logs/ping-assistant
cp launchd/*.plist ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ping-assistant.session.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ping-assistant.watchdog.plist
```

Остановка и удаление:

```bash
launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.ping-assistant.session.plist
launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.ping-assistant.watchdog.plist
rm ~/Library/LaunchAgents/com.ping-assistant.*.plist
tmux kill-session -t ping-assistant   # остановить саму сессию
```

Посмотреть на сессию: `bin/ping-assistant-session` или иконка `Ping Assistant.command`.

### Watchdog

`scripts/watchdog.ts` раз в 5 минут проверяет, что процесс `bun run src/main.ts` этого репозитория запущен. Если сервера нет дольше 5 минут
(короткий перезапуск не считается), шлёт в Telegram (`TELEGRAM_BOT_TOKEN` из `~/.config/ping-assistant/.env`, `telegramChatId` из конфига)
«⚠️ Ping Assistant не запущен. Открой «Ping Assistant.command» или запусти bin/ping-assistant-session»,
не чаще раза в 60 минут. Когда сервер вернулся после алерта, один раз шлёт «✅ Ping Assistant снова работает».
Состояние хранится в `~/.config/ping-assistant/watchdog.json`; если отправка не удалась, оно не меняется и
следующий запуск повторит попытку. Токены и тексты сообщений не логируются, код выхода всегда 0.

### Ноутбук не должен засыпать

`caffeinate -i` уже есть в `bin/ping-assistant-up` и не даёт системе уснуть от простоя. Но с закрытой
крышкой Mac всё равно уснёт, если нет питания и внешнего дисплея, и тогда сервер молчит (watchdog тоже:
он спит вместе с машиной). Держи крышку открытой или работай от сети с внешним монитором.

## Команды в Telegram

Айтемы нумеруются: `#14`, follow-up в том же треде — `#14.1`, `#14.2`.
Под цитатой айтема — свёрнутый блок с тредом/перепиской («Тред · N сообщений» или «Переписка · …»): по строке `ЧЧ:ММ Имя: текст`, свои реплики — «Я», при нехватке места остаются самые новые.

| Что написать | Что произойдёт |
|---|---|
| `14 2` | отправить вариант 2 в Slack как есть |
| `14 2, но короче` | сессия правит вариант и показывает «финальный текст» с кнопками «Отправить/Отмена» |
| `14: свой текст` | отправить свой текст |
| `14 пропустить` | закрыть айтем без ответа |
| `14 да` | подтвердить показанный финальный текст (или отправить, несмотря на предупреждение) |
| `14 ещё` | любой другой текст пересылается сессии как просьба; «ещё» — запросить новые варианты |
| ответ цитатой на сообщение бота | то же самое, номер айтема подставляется сам: «2», «2, но короче», «: свой текст» |
| кнопки `1 2 3`, `Пропустить`, `Отправить`, `Отмена`, `Всё равно отправить` | то же, что команды выше |
| кнопка `👎 разбор` (второй ряд под айтемом, остаётся и после отправки/пропуска) | записать, что разбор или варианты плохие; бот ответит «👎 записал. Что не так?…». Статус айтема не меняется |
| `14 фидбек: слишком длинно` (или `14 fb: …`) | заметка к фидбеку по айтему: дописывается к 👎 за последние 24 ч, иначе новая запись. Цитатой на сообщение бота — просто «фидбек: …» |
| `брифинг` | утренний брифинг прямо сейчас (расписание не сдвигается) |

Текст без номера и без цитаты уходит сессии как обычный чат.

## Проверка dry-run

Slack читается по-настоящему, отправки нет.

1. Slack-приложение, бот, секреты и конфиг по инструкциям выше, `"dryRun": true`.
2. **Смоук без Claude.** `bun run scripts/smoke-check.ts` поднимает `src/main.ts` по stdio и
   ожидает в выводе `started (dry-run)`, `claude/channel capability: yes`, список инструментов
   `propose, ignore, close, list_items, list_ignored, list_feedback, remember_thread, say` и `ok`. В Telegram смоук ничего не шлёт.
3. **Сессия.** `bin/ping-assistant-up`.
4. **Сценарий.** Попросить коллегу написать в личку два сообщения подряд. Ожидается:
   - через `settleSeconds` после последнего — **одно** сообщение в Telegram: шапка
     `#N · личка · Автор`, обе реплики, разбор, 2–3 варианта и кнопки `1 2 3 Пропустить`;
   - нажатие «1» → кнопки у айтема гаснут, в конце строка «✅ отправлен вариант 1», и приходит
     «🧪 dry-run, отправил бы в https://…slack.com/…: <текст варианта>»; в Slack ничего нет;
   - ответ цитатой «2, но короче» → новое сообщение «финальный текст» с кнопками
     «Отправить/Отмена»; у исходного — «✏️ правка ниже»;
   - если коллега успел написать ещё что-то до нажатия — вместо отправки придёт «в треде
     появилось новое» с кнопками «Всё равно отправить/Отмена»;
   - ответ в Slack руками → айтем помечается «🙈 отвечено вручную».
   - самопроверка канала: `PING_ASSISTANT_SELFTEST=1 bin/ping-assistant-up` — примерно через 10 секунд после старта в сессии должно появиться `SELFTEST-OK`.
5. **Остальные сценарии** (каждый — отдельный вопрос от коллеги; в Slack ничего не уходит):
   - **упоминание в канале вне `watchChannels`**: `@ты` в любом другом канале → айтем
     `#N · #канал` в течение `pollSeconds`–2×`pollSeconds` (проверяет синтаксис
     `<@U…>` в `search.messages`; поиск индексирует с задержкой, это нормально);
   - **`#pathfinders`, вопрос верхнего уровня** («кто знает, почему …») → айтем; dry-run
     показывает ссылку на сообщение, отправка пошла бы в его тред;
   - **`#pathfinders`, вопрос в треде** → айтем с контекстом всего треда;
   - **ответ руками в треде**: на вопрос из предыдущего пункта ответить в Slack самому, до
     нажатия кнопки → «🙈 отвечено вручную»; если успел нажать вариант — придёт
     «🙈 #N — ты уже ответил в треде», отправки нет;
   - **правка и старая кнопка**: ответить цитатой «2, но короче», дождаться «финальный текст»,
     потом нажать кнопку «1» на исходном сообщении (если клиент ещё показывает её) или
     «Отправить» на предыдущей правке → «Кнопка устарела, см. #N ниже», ничего не отправлено;
   - **рестарт во время разбора**: пока сессия разбирает айтем (статус `triage` в «что
     висит?», в Telegram по нему ещё ничего нет), выйти из `claude` и снова
     `bin/ping-assistant-up` → тот же айтем приходит в новую сессию заново на ближайшем тике;
     если сессия молчит `triageTimeoutSeconds` — «⏳ #N без разбора уже N мин» с кнопкой «Пропустить»;
   - **MPIM** (групповая личка на троих): вопрос → айтем; твоё сообщение верхнего уровня в этой
     группе айтем **не** закрывает, ответ в треде вопроса — закрывает;
   - **длинный айтем** (>4096 символов, например длинная простыня лога): айтем приходит
     несколькими сообщениями, кнопки на последнем; после правки и нажатия у последнего
     сообщения появляется «✅ отправлен вариант N», живых старых кнопок не остаётся.

## Первая боевая отправка

Когда dry-run прошёл:

1. В `ping-assistant.config.json` поставить `"dryRun": false`, перезапустить `bin/ping-assistant-up`.
2. Дождаться реального вопроса (или попросить коллегу задать) и ответить на него кнопкой с вариантом.
3. Ожидается: в Slack сообщение **от тебя, без бейджа приложения** (в треде, если вопрос был в
   треде; в личке — обычным сообщением); в Telegram у айтема строка «✅ отправлен вариант N»
   и отдельное сообщение «✅ отправлено: <ссылка>», ссылка открывает отправленное сообщение.
4. Самоответ: на другой вопрос ответить руками в Slack. В Telegram у айтема должно появиться
   «🙈 отвечено вручную», кнопки гаснут.
5. Follow-up: если собеседник ответил в треде после твоей отправки, в течение `pollSeconds`
   придёт новый айтем `#N.1` с полным контекстом треда. Слежение выключается через `followUpDays`.

Если что-то пошло не так, вернуть `"dryRun": true`. Живой прогон с настоящими токенами ещё не
делался, поэтому результаты записывать в раздел «Проверено» ниже.
