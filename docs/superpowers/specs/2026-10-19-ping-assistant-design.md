# Ping Assistant — Slack-помощник тимлида. Дизайн

Дата: 2026-10-19. Владелец требований: Илья Лебедюк (тимлид команды Pathfinder, Scentbird). Документ собран по итогам брейншторма и одной проверки независимым строителем. Пометка «(моё решение)» — выбор автора документа, не владельца; такие места можно оспорить, список собран в §10.

## 1. Зачем

Тимлиду приходит много сообщений в Slack, на которые нужно отвечать лично: вопросы по продукту, по коду, по организации работы команды. Каждый ответ требует разобраться (посмотреть код, вспомнить, как работает фича, свериться с Jira/Confluence) и написать текст. Это отнимает часы в день и дробит внимание.

Ping Assistant следит за Slack, выделяет сообщения, где нужно участие Ильи, сам делает разбор, предлагает 2–3 готовых варианта ответа и присылает всё это в Telegram. Илья с телефона или ноутбука выбирает вариант (или правит его), и Ping Assistant отправляет ответ в Slack **от имени Ильи**, без бейджа «через приложение».

**Успех**: большинство входящих вопросов закрываются одним коротким ответом в Telegram («14 2»), качество ответов такое, что команда не отличает их от написанных вручную, и уведомления не превращаются в шум.

## 2. Цели, не-цели, анти-цели

**Цели**
- Ловить всё, где нужен Илья: любая личка в Slack, любое упоминание `@Илья` в любом канале/треде, открытые вопросы «кто-нибудь знает…» в канале `#pathfinders`.
- По каждому пойманному вопросу: разбор + 2–3 варианта ответа в голосе Ильи.
- Отправка в Slack только после явного решения Ильи; ответ уходит от его аккаунта.
- Работает с телефона через Telegram.

**Не-цели (v1)**
- Веб-интерфейс. Возможный второй шаг (страница-артефакт claude.ai с базой), не сейчас.
- Работа при закрытом/спящем ноутбуке. Ping Assistant живёт на маке Ильи.
- Каналы помимо `#pathfinders` и личек (список расширяется конфигом, но v1 ограничен).
- Упоминания user-групп (`@backend` и т.п.) — не ловим в v1 (моё решение; добавляется конфигом `userGroups` позже).
- Автономные действия в Slack: реакции, правки, пересылки, создание тикетов. Только отправка выбранного ответа.
- Обучение голосу внутри Ping Assistant. Гайд по стилю (`voice.md`) готовится отдельно, см. §7.

**Анти-цели (что сделает проект провалом даже если «работает»)**
- **Дробление**: серия из шести сообщений от одного человека («привет», «как дела», «давай к делу», вопрос ч.1, вопрос ч.2, ссылка на тикет) приходит как шесть уведомлений. Должно прийти одно.
- **Частичный ответ**: в одном сообщении три вопроса, а варианты ответа отвечают на один. Каждый вариант должен закрывать все вопросы сообщения.
- **Отправка без подтверждения** — в любом виде, включая «я понял тебя как да». Гарантия должна быть механической, а не только правилом для модели (§4).
- **Голос Claude**: ответ, который звучит как ассистент, а не как Илья.
- **Шум**: уведомление на сообщение, которое не требует ответа Ильи («спасибо», FYI-ссылка, массовый анонс); повторное уведомление по одному и тому же сообщению.
- **Ответ с бейджем** «sent via …» или от бота.

## 3. Ограничения

- Уже есть и используется: Claude Code на маке Ильи с подключёнными Slack (claude.ai коннектор — только для чтения в ходе ресёрча), Jira/Confluence (Atlassian MCP), репозиторий `~/projects/scentbird/backend` на диске.
- Отправка от имени Ильи возможна **только** через пользовательский токен (`xoxp-…`) собственного Slack-приложения. Илья уже создавал приложения в воркспейсе Scentbird, одобрение админа не требовалось.
- Список каналов «со звёздочкой» через Slack API надёжно не достать → список каналов задаётся явно в конфиге.
- Telegram Bot API не даёт истории и поиска. Уведомления Telegram на телефоне у Ильи включены, Slack — выключены (поэтому пульт не в Slack).
- Код проекта: TypeScript, strict mode, запуск через `bun` (channel-серверы Claude Code работают на Bun). Без Python и логики в shell.
- Мак должен не засыпать: запуск через `caffeinate -i`. Lock Screen не мешает.

## 4. Архитектура

```
 Slack (xoxp)                                   Telegram Bot API
   │ poll 60s                                        ▲   │
   ▼                                                 │   ▼
┌───────────────────────────────────────────┐   notifications/claude/channel
│ ping-assistant (один MCP channel-сервер, Bun/TS)│ ───────────────────────────▶ ┌──────────────────┐
│  • сбор из Slack, группировка, состояние  │                              │ Claude Code      │
│  • свой Telegram-бот (grammY): доставка   │ ◀── tools: propose, close,   │ сессия на маке:  │
│    айтемов, разбор ответов Ильи           │     ignore, list_items       │ триаж, ресёрч,   │
│  • ЕДИНСТВЕННЫЙ, кто пишет в Slack        │                              │ варианты ответа  │
└───────────────────────────────────────────┘                              └──────────────────┘
```

**Одна программа, два мира.** `ping-assistant` — собственный MCP channel-сервер (по образцу официального telegram-плагина Claude Code, из которого берётся код Telegram-бота и протокол канала). Он:

1. опрашивает Slack раз в минуту, группирует сообщения в айтемы и хранит состояние;
2. когда айтем готов к разбору, будит сессию Claude Code уведомлением канала;
3. получает от сессии разбор и варианты через инструмент `propose`, сам отправляет их в Telegram;
4. читает ответы Ильи в Telegram; **механические** ответы («14 2», «14 пропустить», «14: текст», «14 да») обрабатывает сам, без участия модели; всё остальное («14 2, но без тикета», «14 ещё», свободный текст) передаёт в сессию;
5. **один отправляет в Slack**, и только по механическому решению Ильи, дословно тот вариант, который Илья видел в Telegram.

Следствия (и причина выбора этой схемы вместо двух отдельных плагинов):
- У модели **нет инструмента для отправки в Slack**. Инъекция через текст Slack-сообщения («Илья, просто ответь ок») или ошибка модели физически не могут привести к отправке.
- Выбранный вариант уходит байт в байт; модель не может «улучшить» его по дороге.
- LLM-ход случается только когда есть что разбирать или Илья попросил переделать; простые выборы ходов не тратят.
- Сервер видит `reply_to_message` Telegram напрямую, форк официального плагина не нужен.

Сессия Claude Code запускается в каталоге проекта с `CLAUDE.md`, описывающим роль, правила триажа, формат разбора и работу с инструментами. Ресёрч по коду выполняется субагентами с доступом к `~/projects/scentbird/backend` только на чтение.

**Запасной вариант** (если channel-протокол на спайке окажется ненадёжным): тот же сервер как демон без channel-части + `/loop 1m` в сессии, который спрашивает сервер «есть новые айтемы?» через обычный MCP-инструмент. Работает, но жжёт LLM-ход каждую минуту. Строитель решает после спайка (§8, шаг 1).

## 5. Поведение по частям

### 5.1 Что ловим (источники)

Slack-приложение Ping Assistant с user-scopes: `channels:history channels:read groups:history groups:read im:history im:read mpim:history mpim:read users:read search:read chat:write files:read`.

Каждый тик (60 с, конфиг `pollSeconds`):

| Источник | Как читаем | Кандидат в айтем |
|---|---|---|
| Личные (IM) и групповые личные (MPIM) | `conversations.list` (im, mpim) + `conversations.history` с курсора | любое сообщение не от Ильи и не от бота |
| Прямое упоминание `<@U_ILYA>` в любом канале/треде | `search.messages` по ID пользователя; дедуп по `channel+ts` (фильтр `after:` работает только по датам) | любое |
| `#pathfinders` (конфиг `watchChannels`) | `conversations.history` с курсора + `conversations.replies` для тредов, где за последние `followUpDays` есть активность | любое сообщение не от Ильи и не от бота |
| Наблюдаемые треды (§5.5) | `conversations.replies` | новые реплики не от Ильи |

Сообщения ботов и системные (join/leave, topic) игнорируются. Сообщения самого Ильи никогда не становятся айтемами, но используются для закрытия (§5.5). `@here`/`@channel` не считаются упоминанием Ильи — в `watchChannels` они проходят обычный триаж, в остальных каналах не видны.

### 5.2 Группировка в айтемы (анти-дробление)

Единица работы — **айтем**: один вопрос (или одно связанное сообщение), требующий одного ответа Ильи. Ключ — разговор (`channel` + `thread_ts`, либо `channel` для IM вне треда) + автор.

- Новое сообщение попадает в **буфер** разговора. Айтем «созревает» и уходит на триаж, когда автор молчит `settleSeconds` (по умолчанию 90) **или** буфер живёт дольше `maxSettleSeconds` (по умолчанию 300). Все сообщения буфера от одного автора в одном разговоре становятся одним айтемом.
- Если в разговоре уже есть айтем в статусе `awaiting` и приходит новое сообщение того же автора, оно **присоединяется** к айтему: Илья получает «#14 дополнение» с новым текстом, а варианты пересобираются, если дополнение меняет суть (решает триаж).
- Сообщения разных авторов в одном разговоре — разные айтемы, каждый с контекстом всего треда.
- Айтем всегда несёт полный контекст: для треда — весь тред; для IM — последние N сообщений (по умолчанию 30) до буфера. Вложения (скриншоты) скачиваются через `files:read` и передаются в сессию путём к файлу.

### 5.3 Триаж и разбор (в сессии Claude Code)

Когда сервер присылает созревший айтем, сессия:

1. **Решает, нужен ли ответ Ильи.** Правило по источнику:
   - IM, MPIM, прямое упоминание: **по умолчанию да**. Исключение — сообщения, где ответ очевидно не нужен: «спасибо», «ок, понял», FYI-ссылка без вопроса, массовое упоминание в анонсе без просьбы к Илье. Такие закрываются инструментом `ignore` с причиной, **без уведомления** (моё решение). Правило при сомнении: присылать.
   - `#pathfinders`: только **открытый вопрос к группе** («кто-нибудь знает…», «почему у нас…», «как работает…») **или прямое обращение к Илье по имени без @** («Илья, глянь PR»). Остальное — `ignore` без уведомления.
   - Реплика в наблюдаемом треде (§5.5): да, если она адресована Илье или продолжает его вопрос; реплики между третьими лицами — `ignore`.
   - Поводы `ignore` логируются; сервер умеет показать их по запросу («что ты проигнорировал за сегодня?»), чтобы правила можно было поправить.
2. **Классифицирует**: `technical` / `product` / `org` / `mixed`. Для `mixed` разбор ведётся по каждому компоненту.
3. **Перечисляет вопросы** внутри айтема. Если их несколько — все явно перечислены в разборе, и **каждый вариант ответа отвечает на все**.
4. **Ресёрчит** по типу:
   - `technical`: субагент (read-only) в `~/projects/scentbird/backend`: код, недавние PR/коммиты по теме, миграции. Итог: что происходит, где, что менялось недавно, гипотеза.
   - `product`: Confluence + Jira (Atlassian MCP), поиск по Slack (claude.ai коннектор) по теме, при необходимости код. Итог: как фича работает сейчас, есть ли тикеты/решения по теме.
   - `org`: файл `team.md` в проекте (состав, расписание дейли/ретро, процессы, ссылки). Если факта нет — вариант ответа честно говорит «уточню», а в Telegram помечается, что `team.md` стоит дополнить.
5. **Пишет 2–3 варианта** в голосе Ильи по `voice.md` (§7), на языке исходного сообщения. Варианты **различаются по сути** (короткий / с деталями / уточняющий вопрос, или разные решения), а не перефразировки.
6. Передаёт серверу инструментом `propose(item_id, analysis, variants[])`. Бюджет: разбор не дольше ~5 минут и не больше одного субагента на тип. Если ресёрч не дал уверенности — это говорится прямо в разборе, и один из вариантов — уточняющий вопрос автору.

### 5.4 Доставка в Telegram и ответы Ильи

Сервер отправляет айтем одним сообщением в личку с ботом (моё решение: личка, не группа; цитирование заменяет треды). Формат:

```
#14 · #pathfinders · Max Darski · 5 мин назад
«…текст вопроса (или склейка серии)…»
<ссылка на сообщение в Slack>

Тип: технический
Вопросы: 1) …  2) …
Разбор: … (3–8 строк, с ссылками на файлы/тикеты, где уместно)

Варианты:
1. …
2. …
3. …

Ответь: «14 1» · «14 2, но без тикета» · «14: свой текст» · «14 пропустить»
[ 1 ] [ 2 ] [ 3 ] [ Пропустить ]      ← inline-кнопки
```

**Кнопки.** Под каждым айтемом inline-кнопки: по одной на вариант плюс «Пропустить». Нажатие приходит серверу как callback и обрабатывается так же, как текстовый «14 N»: вариант уходит в Slack дословно, без участия модели. После нажатия сервер редактирует сообщение: кнопки убираются, вместо них строка «✅ отправлен вариант 2» (или «⏭ пропущен»), чтобы нельзя было нажать дважды и чтобы в ленте был виден исход. Под переработанным текстом (после «14 2, но …») кнопки «Отправить» и «Отмена». Если тред изменился после разбора (см. ниже), кнопки заменяются на «Всё равно отправить» и «Отмена». Текстовые команды остаются как равноценный путь: с клавиатуры, из цитаты, и для правок, которые кнопкой не выразить.

**Новое сообщение или правка старого.** Правка сообщения в Telegram не вызывает уведомление на телефоне, поэтому всё, на что нужно отреагировать (переработанный текст после «14 2, но …», новые варианты после «14 ещё», предупреждение «тред изменился»), приходит **новым сообщением** цитатой на исходный айтем, со своими кнопками. У предыдущего сообщения кнопки гаснут, вместо них строка «✏️ правка ниже». Всё, что лишь фиксирует исход («✅ отправлен вариант 2», «⏭ пропущен»), делается правкой уже существующего сообщения.

Номер айтема берётся из текста ответа **или** из цитаты (`reply_to_message`), если Илья ответил цитатой на сообщение айтема. Варианты хранятся на сервере, поэтому «14 2» работает после рестарта сессии или сжатия контекста.

| Ответ Ильи | Кто обрабатывает | Действие |
|---|---|---|
| `14 2` или кнопка «2» | сервер | отправить вариант 2 в Slack **дословно** |
| `14: <текст>` | сервер | отправить ровно этот текст |
| `14 пропустить` или кнопка «Пропустить» | сервер | закрыть айтем (`skipped`), ничего не слать |
| `14 да` или кнопка «Отправить» | сервер | подтвердить ранее показанный переработанный текст |
| `14 2, но …` / `14 без упоминания тикета` | сессия | переписать, вернуть `propose` с одним вариантом; сервер показывает финальный текст и ждёт «14 да» |
| `14 ещё` / `14 подробнее про X` | сессия | дополнительный ресёрч, новые варианты (новая нумерация) |
| всё остальное | сессия | обычный разговор с ассистентом |

Правило: любой текст, которого Илья не видел дословно, перед отправкой показывается и требует «14 да». Выбор уже показанного варианта уходит сразу.

Перед отправкой сервер проверяет, что в разговоре нет новых сообщений после тех, что видела сессия при разборе. Если есть — показывает их и спрашивает «всё равно отправить? «14 да»».

### 5.5 Отправка в Slack, закрытие, наблюдение

- `chat.postMessage` user-токеном. В канале — всегда в тред исходного сообщения (`thread_ts`). В IM — в тред, если вопрос был в треде, иначе обычным сообщением. Упоминания и ссылки в Slack-разметке.
- После отправки: айтем → `sent`, в Telegram — короткое подтверждение со ссылкой на отправленное.
- **Самостоятельный ответ**: если на тике обнаружено сообщение Ильи в разговоре айтема (статусы `settling`/`awaiting`), айтем закрывается `answered_manually` молча (моё решение).
- **Наблюдаемые треды** (моё решение, узкое правило): только (а) треды, куда Ping Assistant отправил ответ, (б) треды в `watchChannels`, где Илья писал сам, (в) личные разговоры — они наблюдаются всегда по определению. Треды в прочих каналах, где Илья писал сам, **не** наблюдаются (иначе каждая реплика в живом обсуждении становится айтемом). Наблюдение живёт `followUpDays` (по умолчанию 7).
- **Продолжение**: новая реплика в наблюдаемом треде проходит триаж (§5.3 п.1) и, если нужна, создаёт айтем с тем же номером и суффиксом (`#14.2`) с полным контекстом треда.

### 5.6 Состояние и идемпотентность

- Состояние сервера — один JSON-файл (`~/.config/ping-assistant/state.json`, моё решение; SQLite, если строитель сочтёт нужным): курсоры по разговорам, буферы, айтемы со статусами, разбором и вариантами, соответствие айтем ↔ Telegram message_id, наблюдаемые треды, журнал `ignore`.
- Ключ дедупликации — Slack `channel + ts`. Сообщение, уже попавшее в айтем, никогда не создаёт новый.
- При перезапуске сервер продолжает с курсоров; айтемы в `awaiting` продолжают ждать.
- При первом запуске курсоры ставятся на «сейчас»: прошлое не разбирается.

### 5.7 Статусы айтема

`settling` → `triage` → (`ignored` | `awaiting`) → (`sent` | `skipped` | `answered_manually`) → наблюдение треда до `followUpDays`.

## 6. Как это запускается

- Каталог: `~/projects/ping-assistant` (моё решение), отдельный git-репозиторий, не монорепа Scentbird.
- Структура (ориентир):
  - `server/` — ping-assistant channel-сервер (Bun/TS): `slack/` (сбор, отправка), `telegram/` (бот, по образцу официального плагина), `items/` (группировка, состояние, парсер ответов), тесты на группировку, дедуп и парсер.
  - `CLAUDE.md` — инструкции сессии: роль, §5.3–5.4 как правила, ссылки на `voice.md`, `team.md`, путь к репозиторию Scentbird. Сессия работает без присмотра, поэтому нужные разрешения (чтение репозитория, Atlassian/Slack MCP на чтение, инструменты ping-assistant) заранее внесены в allowlist настроек проекта.
  - `voice.md`, `team.md` — данные; `voice.md` готовится отдельно (§7), `team.md` заполняет Илья.
  - `ping-assistant.config.json` — `userId`, `watchChannels`, `settleSeconds`, `maxSettleSeconds`, `followUpDays`, `scentbirdRepoPath`, `pollSeconds`, `telegramChatId`.
  - `bin/ping-assistant-up` — запуск: `caffeinate -i claude --channels <ping-assistant>` из каталога проекта.
- Секреты: `~/.config/ping-assistant/.env` (`SLACK_USER_TOKEN`, `TELEGRAM_BOT_TOKEN`). Ни один токен не попадает в репозиторий.
- Установка: `bun`, Slack-приложение со scope-ами из §5.1, Telegram-бот через BotFather, allowlist по Telegram user ID Ильи (чужие сообщения отбрасываются молча).

## 7. Голос Ильи (`voice.md`)

Отдельный шаг до первого реального ответа: Илья просит Claude прочитать его личные сообщения в Slack за период и вывести гайд по стилю — язык по ситуации, длина, тон, обращения, типичные обороты, чего он не делает. Гайд живёт в `voice.md`, сессия следует ему при написании вариантов. Пока `voice.md` нет, варианты пишутся нейтрально, и в Telegram помечается «voice.md не найден».

## 8. Порядок внедрения (рекомендация строителю)

1. Спайк channel-протокола: минимальный сервер, который по таймеру присылает в сессию «тик» и имеет один инструмент. Подтверждает, что уведомление будит сессию и инструменты доступны. Здесь же решение про запасной вариант (§4).
2. Telegram-часть сервера: бот, allowlist, отправка, inline-кнопки и callback, парсер механических ответов, тесты парсера.
3. Slack-коллектор: IM + упоминания + `#pathfinders`, группировка, состояние, тесты.
4. `CLAUDE.md` сессии и инструменты `propose`/`ignore`/`close`/`list_items`; прогон на реальных входящих в режиме **без отправки в Slack** (флаг `dryRun`: «14 2» пишет в Telegram «отправил бы: …»).
5. Отправка в Slack от имени Ильи, проверка самоответа, наблюдение тредов, проверка «тред изменился».
6. `voice.md`, затем первые реальные ответы.

## 9. Оставлено строителю

- JSON vs SQLite для состояния; внутренняя структура айтема.
- Точный алгоритм поиска упоминаний и обработка лимитов Slack API.
- Способ запуска субагентов для ресёрча и их бюджеты.
- Формат `team.md`.
- Логирование и диагностика (где смотреть, почему айтем не пришёл или почему проигнорирован).
- Сколько кода брать из официального telegram-плагина (Apache-2.0) и как.

## 10. Решения автора документа, которые стоит проверить владельцу

1. **Один сервер вместо «telegram-плагин + свой Slack-канал»** (§4). Причина: механическая гарантия «без подтверждения ничего не уходит» и дословная отправка выбранного варианта. Цена: Telegram-бот пишется внутри проекта, а не берётся из плагина (код можно переиспользовать).
2. **«Спасибо» и FYI в личке/упоминаниях закрываются молча**, без уведомления (§5.3). При сомнении — присылать.
3. **Обращение по имени без @ в `#pathfinders`** считается поводом (§5.3).
4. **Упоминания user-групп не ловим** в v1 (§2).
5. **Наблюдаем только** треды Ping Assistant, личку и треды в `#pathfinders`, где Илья писал сам (§5.5).
6. **Самоответ закрывает айтем молча** (§5.5).
7. **Личка с ботом, а не группа** в Telegram (§5.4).
8. Каталог `~/projects/ping-assistant`, состояние в JSON, имя Ping Assistant.
